# 落地流 · 体验官审阅编排

## 何时用

- 一个可运行的成品（或可体验的完整模块）做完了，**在交给用户之前**。
- 用户说"不好玩 / 没感觉"之后返修完，要再交一次之前。
- 阶段性里程碑（前 5 分钟体验成立）想先自查时。

**不适用**：单元测试、构建、数据正确性——那是 `deep-construction-delivery` 的真实验证清单，不是体验审阅。

## 为什么需要这一层

**用户是最终验收者，不是第一个体验者。** 你把半成品丢给用户说"你看看"，就是把设计债转嫁给用户。用户会看到"第一次想放弃的时刻"，然后失去信心——而这个时刻本该由你在交付前发现并修掉。

## 六位体验官

| 体验官 | 切面 | 启用条件 |
|---|---|---|
| 初见官 | 时间轴 t=0–5 分钟冷启动 | 总是 |
| 核心循环官 | 乐趣与动机 | 有重复性核心动作的产品 |
| 留存官 | 第 2、3 次会话 | 有长期使用/游玩预期的产品 |
| 学习官 | 学习有效性 | **仅学习类**（语言、知识、技能训练） |
| 可用性官 | 跨品类可用性 | 总是 |
| 对抗官 | 元层找反例 | 总是，**且最后跑** |

**不要六位全派。** 按产品类型选：纯工具可跳过核心循环官与留存官；学习类必须加学习官；娱乐产品必须加核心循环官与留存官。

## 硬规则（违反任何一条，这次审阅作废）

1. **必须用独立子代理跑**（`subagent`），全新上下文。
2. **它只看成品与用户的原始意图**——不读 README、设计文档、施工日志、你的推理、以及别人的报告。
3. **必须先真跑真看再下结论。** 证据是截图路径、坐标、时间戳、命令与原始输出。
4. **不得修改任何代码。** 只报告，不修。
5. **每人至少交 2 条"最可能被真人差评的点"和 1 条"什么观察会推翻我"。** 零反例的报告直接退回。
6. **对抗官必须至少推翻或降级 1 条他人结论。** 一条都推翻不了，视为审阅流程失败。
7. **说"通过"必须同时指出"第一次想放弃的时刻"和"想再用的具体理由"。** 两个都指不出来，默认不通过；**禁止输出"整体良好"**。

## 派发模板（照抄改）

派每一位时都用这个形状：

```
你是一名独立体验官，任务是从"人"的角度审阅一个已完成的成品。你没有参与它的开发，也不需要体谅开发者的难处。

先加载技能 deep-construction-reviewer-<官名>，按其中的 rubric 审阅。

【你只能看这些】
- 成品入口：<启动命令 / URL / 可执行文件路径>
- 用户当初的原话：<逐字原文，不改写>
- 用户已确认的偏好：<取向光谱等>

【你绝对不能看】
README、设计文档、施工日志、代码注释里的设计说明、上一位体验官的报告。
理由：你要复现的是"一个陌生人第一次接触它"的体验，不是"读懂了设计意图之后的评价"。

【你必须做的】
1. 真的把它跑起来，按 rubric 走完整流程。
2. 每一步留下证据：截图路径 + 时间戳 + 坐标，或命令 + 原始输出。
3. 按 rubric 逐条判定，每条结论前先给证据。没有证据的结论标"未验证"，不计入通过。

【你不能做的】
- 不能修改任何代码或文件。
- 不能凭代码"看起来对"就判定通过。
- 不能给出"整体良好""体验不错"这类无证据结论。

【交付格式】
1. 逐条判定表（条目 / 判定 / 证据）
2. 通过或不通过（rubric 的通过标准）
3. 第一次想放弃的时刻（精确到第几秒/哪一步）
4. 想再用的具体理由（指不出就写"指不出"）
5. 至少 2 条最可能被真人差评的点
6. 1 条"什么观察会推翻我的结论"
```

**不要把 rubric 正文复制进提示词**——让它自己加载技能，省你的上下文，也保证 rubric 只有一份。

## 编排流程

1. **判定产品类型**，选启用哪几位。
2. **同一入口分发给所有人**（同一条启动命令 / 同一个 URL）。
3. **并发派发**（除对抗官），每人一个独立子代理。
4. **收报告**，把每位的 `officer / status / isolation / report / evidence / verdict` 写进 `d_state.reviewers`。
5. **派对抗官**，提示词里附上其他人的结论摘要，要求它逐条反驳。
6. **仲裁**：有冲突时按证据判，**不靠投票**。对抗官推翻成立的结论，要求对应体验官重修或产品返修。
7. **全部通过**（或退回重修后再通过）才交给用户做最终验收。

## ⚠️ 收尾是显式步骤，不要指望还有下一轮（真机教训）

`subagent` **默认后台执行**：派出去只会拿到"已启动"，不会拿到结论。真机实测 `acceptance\run6` 里踩到过这个坑——模型派了 4 位体验官、自己继续干活（并行是对的）、两次 `list_agents` 都还是 `[running]`，然后**带着"审阅进行中 4/5"结束了本轮**，`d_state.reviewers` 从头到尾是空的：

- 宿主的橡皮图章检查永远等不到数据，**保护形同不存在**；
- 用户在面板上看不到任何审阅结论；
- 单轮任务就此丢失了已经跑出来的四份报告。

**规矩：**

1. 派体验官时**显式设 `run_in_background: false`**（你能拿到结论再往下走）；确实要后台并行时，就必须在结束本轮之前用 `list_agents` 确认全部退出，再 `send_message` 或读回报告。
2. **`d_state.reviewers` 是这次审阅的交付物之一**，不是副产品。报告拿到就写，拿到一份写一份——不要攒到最后。
3. 如果确实来不及（本轮上限到了），**不许交"审阅进行中"当结果**：要么明确把状态停在体验官审阅阶段并写清还差谁，要么就不说"可以交付"。**宁可报没做完，也不要让用户以为已经过了审阅。**

## 写回状态

```
reviewers: [
  { officer: 初见官, status: 通过, isolation: 独立子代理, report: "reports/初见官.md",
    evidence: "shot-01.png @0s / shot-02.png @12s / 首次成功用时 34s", verdict: "通过：…；第一次想放弃：第 41 秒不知道要干什么", agent_id: "…", date: "2026-10-09" },
  { officer: 对抗官, status: 不通过, isolation: 独立子代理, overturned: "推翻 留存官 第 3 条（它说的回归钩子其实是空进度条）", … }
]
```

**`isolation` 必须如实写。** 不是「独立子代理」的"通过"会被宿主判为橡皮图章并直接报错——那是模式在保护用户。

## 退回之后

体验官给"不通过"属于**业务失败**，不是主观噪音：

- 回到 DESIGN / BUILD 修，在 `repair_history` 里记一轮，**不允许当"事后打磨"打补丁**。
- 修完**重跑对应体验官**（换一个新的独立子代理，不要复用上一个的上下文）。
- 用户的"不好玩 / 没感觉"同理，而且优先级更高。

## 反橡皮图章自查

交付前问自己：

- [ ] 每位体验官都是独立子代理吗？
- [ ] 它真的跑了成品吗（有截图/输出），还是只读了代码？
- [ ] 有没有人交出"零反例"报告？（有就退回）
- [ ] 对抗官推翻了几条？（0 条 = 审阅流程失败）
- [ ] 有"通过"结论说不出"第一次想放弃的时刻"吗？（有就默认不通过）
- [ ] 我有没有把体验官的结论改写得更好听？（不许）
