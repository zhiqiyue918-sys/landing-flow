# 落地流 · 成熟底座优先复用，原创集中在产品核心

原则：**"自己写"不是价值；"更符合最终产品目标"才是价值。**

## 复用阶梯（默认顺序）

对每个专业模块依次判断：

1. 能否直接复用成熟方案？
2. 能否组合多个成熟能力？
3. 是否只需要一个薄适配层？
4. 是否只需局部改造？
5. 现有方案是否确实无法满足目标？
6. 只有确认不满足时，才从零原创。

优先级：`直接复用 > 组合成熟方案 > 薄层适配 > 局部改造 > 从零原创`

## 通常不值得从零原创

常规存储、日志、打包、更新、网络请求、UI 基础组件、标准算法、浏览器自动化、常规身份认证、通用文件系统能力、常见游戏输入/音频/碰撞/寻路、已成熟的协议/框架/工具链。

## 原创应该集中在哪里

产品独特核心、独特玩法、核心机制、用户体验、产品逻辑、世界规则、用户独有工作方式、成熟方案无法满足的差异化能力。

## 原创前必须回答（答不出就不算决定）

1. 成熟方案具体缺在哪里？
2. 为什么组合 / 适配仍不足？
3. 真正需要原创的核心是什么？
4. 原创部分如何和成熟基础设施组合？
5. 原创会增加哪些成本、风险和维护负担？

把这 5 个答案写进对应模块的说明与 `d_state.decisions`。

## 参考物的层级判断

用户给出游戏、产品、界面、图片、视频、代码、方法或其他参考物时，先判断参考的是哪一层：核心玩法、数值、美术风格、UI、动画表现、交互、技术底层、架构、内容组织、某个局部机制。

某一层相似，不授权其他层自动跟随。用户说"画面像 A"，不能自动照搬 A 的玩法、架构、数值。

## 普通技术选择不要反问用户

React / Vue、SQLite / IndexedDB、Electron / Tauri、某个成熟库、内部目录结构、普通状态管理方式等，如果不明显改变用户真正关心的体验、成本、平台、隐私或长期方向，由你自己研究、比较、选择，并只回执「用了什么、为什么」。

## 输出格式

模块方案汇报时给出三段：

```
复用：<成熟方案清单 + 用途>
原创：<本产品核心 + 为什么必须原创>
组合：<原创部分如何接在成熟底座上>
```

## 常见错误

- 为了"可控"重写成熟基础设施。
- 为了省事把产品核心也外包给通用方案，导致差异化消失。
- 复用了但没说明为什么，用户看不到专业性。
- 把参考物的某一层当成整体授权。
