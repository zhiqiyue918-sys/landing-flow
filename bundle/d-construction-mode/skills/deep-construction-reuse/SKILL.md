# 落地流 · 成熟底座优先复用，原创集中在产品核心

原则：**"自己写"不是价值；"更符合最终产品目标"才是价值。**

## 第 0 层：先定承载平台，再谈模块复用（别一个人单打独斗）

在讨论"这个模块怎么实现"之前，先回答一个更大的问题：**这件作品靠什么承载？**

模块级复用做得再好，也救不了"整体从零手写"。真实教训：一个单文件滑翔游戏，物理、渲染、音频图、输入、存档**全部手写**，从头到尾**一次都没提过任何游戏引擎**——而当时连"用不用引擎"这个问题都没被问出来。这就是单打独斗：不是能力不够，是**根本没去查生态**。

### 候选平台（先查再选）

| 品类 | 先查这些 |
|---|---|
| 游戏 / 交互体验 | **Godot**（MIT、2D/3D、导出 Web/桌面/移动）、**Unity**、**Unreal**、**GameMaker**、**Construct 3**（无代码）、**RPG Maker**（JRPG）、**Phaser**（Web 2D）、**Cocos Creator**、**LÖVE**、**Bevy**（Rust）、**Defold** |
| 桌面应用 | **Electron**、**Tauri**、**Qt**、**WinUI / WPF**、**.NET MAUI**、**Flutter** |
| 交互网页 / 可视化 | 浏览器原生（Canvas 2D / WebGL / WebGPU / Web Audio / Web Animations）、**Three.js / PixiJS / Babylon.js**、**D3** |
| 内容 / 工具类 | 成熟编辑器与运行时的组合，不要自己写编辑器 |

### 先扫本机，再谈"要不要下载"

在写任何 `why_not` 之前，**先查这台机器上已经有什么**：`Get-Command`、常见安装位、`tools\` 目录、PATH、以及用户以前的工程目录。真实教训：一次真机跑以「Godot 需要额外下载约 1.1GB 导出模板」为由否决 Godot——**而 Godot 4.7 早就装在本机**（`Y:\codex\墨劫行\tools\godot\`）。

先扫本机的好处有两层：

1. **少一条假的 why_not**。因为没查而写下的"要下载/装不了"，是错误结论，会让用户白丢一个更省事的方案。
2. **顺带找到用户已有的工作流**：以前的游戏工程目录里往往带着引擎、导出模板、图标库、音频素材和可复用的脚本约定，这些比网上重新找的更贴合这台机器。

注意仍是硬约束优先：本机有引擎 ≠ 就该用。如果交付形态把它排除了（单文件、file:// 双击即玩、包体上限），那照样否决它——但 why_not 要写成真实约束，而不是"要下载"。

### 挑了这些子系统就是警报

只要你在手写下面任何一项，先停下来问"是不是有现成平台已经做好了这个"：

> 物理与碰撞、渲染管线与着色器管理、场景图与图层、动画与缓动时间轴、粒子系统、UI 布局与控件库、输入映射与手柄支持、存档与设置、
> 本地化、资源打包与热重载、寻路、音频混音与总线、编辑器与关卡工具、导出与打包流水线。

这些在成熟引擎里都是**默认就有**的东西。手写它们只有在交付形态强硬约束下才成立（见下）。

### 自研的举证责任

选择 `无框架自研` **合法**，但必须付出举证成本，写进 `d_state.platform`：

```
platform.choice：<平台名 + 版本>          # 自研就写真话，例如「自写 Canvas 2D 引擎」
platform.kind：游戏引擎 / 应用框架 / 浏览器原生 / 原生平台 / 宿主游戏 mod / 无框架自研 / 其它
platform.alternatives：[{ name, why_not }] # 选「无框架自研」时**至少 2 个**，且每个都要有 why_not
platform.licence / cost / export_targets / note
```

### 宿主游戏 mod：承载平台是别人的游戏

做 mod 时"用哪个引擎"是错的问题——**你不是在做独立产品，你是在往别人的游戏里加东西**。这时 `kind` 写 `宿主游戏 mod`，并且必须多写三个字段：

```
platform.host_game    ：宿主游戏（例：「Minecraft Java 版」）
platform.host_version ：**锁定的那一个**宿主版本（例：「1.20.1」）
platform.host_loader  ：加载器及版本（例：「Forge 47.2.0」）
```

**这三样不是备注，是决定产物能不能被加载的东西。** 宿主游戏每个大版本都改过 API，加载器（Forge / NeoForge / Fabric / Quilt）又是各自独立的生态——为其中一套编译的 jar，装到另一套上**根本不会被载入**。

**先别急着填引擎。** mod 最常见的错是 `kind` 顺手写了「游戏引擎」——那是**独立产品**的类别。写错了会**绕过全部 mod 检查**（版本锁定、加载器绑定、验收要带宿主），最后交付一个不知道装在哪个版本上的 jar。宿主会核对 `choice` / `note` 里的字眼（`mod` / 模组 / Forge / Fabric / Paper / 数据包……），写「游戏引擎 + Minecraft Forge mod」会被判缺陷。

两条纪律：

- **版本与加载器是规格题，必须问用户**（§提问纪律）。他朋友装的是哪个版本、用的哪个启动器，只有他知道。**不许替他默认**，也不许因为"最新版看起来更好"就自己定。
- **`host_version` 必须是一个具体的版本号。** 两种写法都会被判缺陷：
  - **"多版本"**——"支持多版本"不是一个可以声称的属性，它是**分别编译的多份产物**：跨 MC 大版本意味着多套源码、或一套多目标构建（如 Architectury），外加逐版本的真机验证。
  - **模糊写法**——`最新版` / `1.20.x` / `1.20 以上` / `任意版本`。这些读起来像版本，**其实什么都没锁定**。

  **首版锁定唯一一个具体版本**（如 `1.20.1`），其余写进 `note` 作为后续计划，并说清代价。

**`host_version` 与 `host_loader` 可以写在一起**（`1.20.1 + Forge 47.2.0` 这类写法是合法的）——但**具体版本号必须出现**。

**先扫本机已有的东西再开口问**：启动器安装目录、`.minecraft/versions`、整合包的 `mods/` 目录（里面的 jar 文件名通常带着 `1.20.1-forge` 这类字样，直接告诉你用户在玩什么）、以及有没有可用的 JDK。这些是能从环境里读出来的事实，不要拿去问用户。

`why_not` 必须是**具体约束**，不许写"太复杂""不熟悉""更可控"：

- 交付形态：单文件、离线、双击即玩、file:// 直开、包体上限；
- 许可与费用：是否可商用、是否有收入门槛、是否按席订阅、导出目标是否额外收费；
- 导出与平台覆盖：能不能导出到用户要的目标（Web / 桌面 / 移动 / 主机）；
- 包体与性能：引擎运行时体积（Godot Web 导出是 wasm + pck，通常几 MB 到十几 MB，且 file:// 下部分能力受限）；
- 维护状态与长期风险：最近提交、版本节奏、社区规模；
- 用户已明确排除的东西（例如"不要外部依赖"）。

**写不出 why_not，就说明你没查过——回去查，不要继续手写引擎。**

### 什么时候自研是正确答案

- 交付形态硬约束把引擎排除掉了（例如「单文件、零依赖、file:// 双击即玩」——这时浏览器原生 Canvas/Web Audio 是**经过比较后的正确选择**，但必须把 Godot/Phaser 等候选和 why_not 写下来）；
- 用户明确要求从零实现作为学习或研究目的；
- 那个子系统**本身就是产品核心**（例如你卖的就是一个物理引擎）。

注意区别：**"引擎不适合这个交付形态"**是对的；**"我没想过用引擎"**是错的。前者要留证据，后者要被判缺陷。

## 复用阶梯（默认顺序）

对每个专业模块依次判断：

1. 能否直接复用成熟方案？
2. 能否组合多个成熟能力？
3. 是否只需要一个薄适配层？
4. 是否只需局部改造？
5. 现有方案是否确实无法满足目标？
6. 只有确认不满足时，才从零原创。

优先级：`直接复用 > 组合成熟方案 > 薄层适配 > 局部改造 > 从零原创`

## 通常不值得从零原创

常规存储、日志、打包、更新、网络请求、UI 基础组件、标准算法、浏览器自动化、常规身份认证、通用文件系统能力、常见游戏输入/音频/碰撞/寻路、已成熟的协议/框架/工具链。

## 原创应该集中在哪里

产品独特核心、独特玩法、核心机制、用户体验、产品逻辑、世界规则、用户独有工作方式、成熟方案无法满足的差异化能力。

## 原创前必须回答（答不出就不算决定）

1. 成熟方案具体缺在哪里？
2. 为什么组合 / 适配仍不足？
3. 真正需要原创的核心是什么？
4. 原创部分如何和成熟基础设施组合？
5. 原创会增加哪些成本、风险和维护负担？

把这 5 个答案写进对应模块的说明与 `d_state.decisions`。

## 参考物的层级判断

用户给出游戏、产品、界面、图片、视频、代码、方法或其他参考物时，先判断参考的是哪一层：核心玩法、数值、美术风格、UI、动画表现、交互、技术底层、架构、内容组织、某个局部机制。

某一层相似，不授权其他层自动跟随。用户说"画面像 A"，不能自动照搬 A 的玩法、架构、数值。

## 普通技术选择不要反问用户

React / Vue、SQLite / IndexedDB、Electron / Tauri、某个成熟库、内部目录结构、普通状态管理方式等，如果不明显改变用户真正关心的体验、成本、平台、隐私或长期方向，由你自己研究、比较、选择，并只回执「用了什么、为什么」。

## 输出格式

模块方案汇报时给出三段：

```
复用：<成熟方案清单 + 用途>
原创：<本产品核心 + 为什么必须原创>
组合：<原创部分如何接在成熟底座上>
```

## 常见错误

- 为了"可控"重写成熟基础设施。
- 为了省事把产品核心也外包给通用方案，导致差异化消失。
- 复用了但没说明为什么，用户看不到专业性。
- 把参考物的某一层当成整体授权。
- **没查生态就从零手写**：上来就写引擎的物理/渲染/音频/输入/存档，一次都没提过现成引擎或平台。这是"一个人单打独斗"，是本技能要防的头号错误。
- **把"自研"当默认**：`无框架自研` 是结论，不是起点。没有 ≥2 个候选和具体 `why_not`，就不是选择，是没做功课。
- 用"更可控""不熟悉""太复杂"当 why_not——真实原因只能是交付形态、许可费用、导出目标、包体性能、维护状态这类硬约束。
