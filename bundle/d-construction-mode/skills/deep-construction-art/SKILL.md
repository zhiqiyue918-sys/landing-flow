# 落地流 · 美术达标

## 何时用

- 某个交付板块的 `art_weight` 是 **S** 或 **A**（画面本身是卖点 / 重要）。
- 你在写任何绘制代码之前、之中、之后——**不是只在收尾时用**。
- 你自己（或用户）觉得画面"一般""粗糙""还行但差点意思"。
- 你要填 `d_state.art`（`references / palette / layers / light / texture / ui / view_rounds`）。

## 第一原则：不要对着形容词做

**「要好看」「要有氛围」「剪影渐层」这类描述不能作为美术方案。** 它们不可验证，所以做不出好东西，也没法判断做完没有。

形容词的替代品是两样东西：**参考图**，和**色板**。

## 第一步：找参考（≥2 张，每张写清抄什么）

参考的来源，按可信度排：

1. **用户给的图**——最高优先，直接代表他要什么。
2. **同品类的商业作品截图**——看它们**怎么做**的，不是看它们长什么样。
3. **素材包/引擎的示例图**（Kenney、Poly Haven、Godot 官方 demo）。
4. **真实照片**（风景、光照、材质）——做氛围时比插画更有用。

每一张必须写 `what_to_steal`。**写不出"抄什么"，说明你只是觉得它好看，那不算参考。** 要抄的通常是这些：

- 分层数量与层间距（几层？每层差多少？）
- 明暗对比关系（最暗/最亮落在哪一层？）
- 色相往哪偏、饱和往哪走（**不要只抄明度**）
- 材质怎么做（噪点强度、颗粒、笔触、渐变方向）
- 角色剪影的形状语言（统一特征是什么？尖端？圆钝？带角？）
- 细节密度（一屏里有多少可辨识的小元素？）
- 光线怎么进入画面（光源位置、有没有体积光、有没有被遮挡的衰减）

## 第二步：色板要带 hue 推移（这一步最便宜、效果最大）

**只用明度差做远近 = 一片脏灰。** 这是实测里被判"粗糙"的头号原因。

深度方向的规定动作：

| 层 | 明度 | 饱和度 | 色相偏向 |
|---|---|---|---|
| 远景 | 提高（靠拢天空） | **降低** | **冷**（蓝 / 青 / 紫） |
| 中景 | 中 | 中 | 中性 |
| 近景 | 降低（更实） | **提高** | **暖**（橙 / 红 / 褐） |

- `art.palette` 至少 **4 个不同色值**，每条 `hex + role`，写具体的 `#2B3A55`，不写"深蓝"。
- 先定 3–5 个主色（天/远/中/近/角色），再派生明暗变体。
- **角色必须与背景有分离手段**：颜色对比、明度对比、或**边缘光**。背景暗的时候角色不能也是暗的。

## 第三步：对比迭代（≥3 轮，宿主会查）

**一轮的定义**（全做完才算一轮）：

1. **渲染**——走用户会打开的同一条路径。
2. **真的看**——有视觉能力就 `vision_*` 真看；没有就交给用户看。**不许用文字描述代替看图。**
3. **与参考并排比**——把成品和参考放一起，问"差在哪"，要指到元素（"第 2 层和第 3 层的色相太近""夜里角色读不出轮廓""草的线段太随机"）。
4. **列差距**——写进 `gaps`。
5. **改一处**——写进 `changed`。**只看了没改（`changed` 为空）不算迭代**，宿主会判缺陷。
6. 回到第 1 步。

一轮就是一张截图。三轮才是循环。**实测那次粗糙的成品，是 0 轮。**

### 证据帧必须等于实机

**这条比前三条都重要。** 审视用的截图必须来自**用户会打开的同一条路径**：同一个文件、同一段代码、同一种进入方式（同一个 URL、同一个入口点、同一套参数）。

实测教训：那次它自己另写了一个渲染脚本，导出的帧**比实机亮得多、层次清楚得多**——于是它拿美化过的帧给自己判了"通过"，而用户打开实机看到的是更暗更糊的版本。**用美化的帧当验收证据，比没有证据更糟**：它会让一个真问题被"证据"掩盖掉。

自检问句：*"我这张图，用户双击打开能看到一模一样的东西吗？"* 答不上来，就不是证据。

## 第四步：把"粗糙"逐项排掉

对着这张表逐条查，每条都要能指出具体做法：

| 症状 | 检查 | 合格线 |
|---|---|---|
| **脏灰** | 是不是只有明度差？ | 有 hue/饱和度推移，≥4 色 |
| **纯平涂** | 有没有任何材质手段？ | 至少一种：噪点/颗粒/笔触/渐变/纹理叠加 → `art.texture` |
| **画面是死的** | 光源有没有影响场景？ | 受光面/背光面有区别；日月不是贴上去的圆 → `art.light` |
| **角色像纸片** | 有没有从背景里"跳"出来？ | 颜色/明度对比，或边缘光 |
| **层次糊** | 相邻层色差够不够？ | 滚动时一眼分得开 |
| **形状语言随机** | 细节是同源的还是随机的？ | 统一的形状特征（`Math.random()` 画线段不算） |
| **焦点错** | 第一眼看哪里？ | 焦点在角色/目标上，不在光晕上 |
| **细节密度低** | 一屏有多少可辨识元素？ | 背景有大面积纯色块 = 不合格 |
| **UI 业余** | 字体、对比度、层级、对齐 | 非系统默认字体；对比度够；层级清楚 → `art.ui` |

## 第五步：能力边界要诚实

- **有视觉能力**（会话开了「👁 识图」）：必须真的看，`view_rounds.looked_at` 写清看了哪张。
- **没有视觉能力**：**不得声称达标**。正确动作是——"我渲染了这些帧，请你告诉我哪里不对"，把帧给用户，或等识图开了再迭代。
- **永远不许**用文字描述代替看图，也不许把"应该挺好看"写成结论。

## 零依赖 ≠ 不能有真美术

"单文件 / 零外部依赖"限制的是**外部文件**，不是美术质量。可以内嵌：

- **base64 图片**（真实素材包里的图直接内联，双击即玩、零依赖）
- **内联字体子集**（避免系统默认字体的业余感）
- **预生成的纹理/噪声贴图**（内嵌后当贴图用，比实时算噪点更可控）
- **SVG**

程序化绘制是**手段**不是目的。当艺术是卖点、手上又只有代码时，顺序是：**能不能内嵌真实素材？→ 能不能用引擎/框架自带的美术能力？→ 最后才是手写。**

## 常见错误

1. **"风格契约"写成了形容词**——「剪影渐层」「要有氛围」不是契约。契约是色板 hex、层数、光照方向、材质做法。
2. **只渲染一次就收工**——没有对比就没有迭代，`view_rounds` 会少于 3 轮，宿主直接判缺陷。
3. **用自己另写的渲染脚本当证据**——实机比你导出的帧暗/糊时，你等于在骗自己。证据帧必须等于实机。
4. **只用明度差分层**——这是"粗糙"最常见的单一原因，也最便宜就能修。
5. **细节用随机数生成**——草、石头、粒子都随机 = 没有形状语言 = 廉价感。
6. **光源只是贴图**——日月不照亮场景，画面就永远是平的。
7. **角色和背景同色系同明度**——玩家找不到自己在哪。
8. **UI 用系统默认字体**——一眼业余，且往往对比度不达标。
9. **"没视觉能力"却写"我觉得挺好"**——这是最严重的诚实问题，也是本机制存在的理由之一。
10. **把美术当收尾项**——美术方向要在 DESIGN 定，不能等代码写完再"加点颜色"。
