# 落地流 · 开工文档（Kickoff Dossier）

## 何时用

- 任务刚开始，还没写进 `d_state.construction_brief` 的正式 Brief 之前。
- 用户给的是一句话题材（"做一个增量游戏""做一个背单词软件"）。
- 用户只会讲感觉、讲不清需求时（见本文末「感觉流派翻译法」）。

**核心判断：这份文档是模式最重要的第一次交付，必须发生在任何施工之前。** 用户最怕的不是被问，而是做到一半又要改——所以问题要在开局一次问完，而不是跑起来碰到一个问一个。

## 产出物

1. 一份**真实文件**：`<项目>/开工文档.md`（大项目放 `docs/开工文档.md`）。
2. 一条 `d_state` 更新：

```
kickoff: { status: 已发出, path: <文件路径>, question_count: "<N>", blocking_count: "0" }
intake:  { status: 已发出, autonomy: 未授权, note: "一次问全覆盖了 …" }
pending_user_decisions: [ 每条 { question, status: 待回答, level: 黄, fallback, asked_at, timeout_min: "40" } ]
```

3. 回执里给出文件路径，并说明普通默认项的推进规则。**游戏方案、核心玩法、画风品味和“是否喜欢/是否需要这款游戏”不能因用户沉默或 40 分钟超时自动通过。** 用户回答开工文档问题，只代表补充条件；必须另有“我选这个方案/我喜欢这个方向/按这个方案开工”的明确证据。

## 文档骨架（照抄，不要另创格式）

```markdown
# <产品名> 开工文档
- 你的原话：<用户原始需求的原文，一个字都别改写>
- 我理解的目标：<一句话>
- 怎么用：在你关心的条目下写答案；不想答的跳过，我会按「推荐默认值」做并留痕。

## 一、我理解的，请你确认或纠正
1. …
2. …

## 二、需要你定的（每条都有推荐默认值；你不回我按默认做）
### Q1 <问题>
- 选项：A … / B … / C …
- 为什么问：<这件事会改变产品的哪个部分>
- 我的推荐默认值：<A，因为…>
- 你不回：我按 A 推进（标黄，40 分钟后自动推进），你随时可以推翻

### Q2 …

## 三、我按默认做、你随时可改的（不必现在看）
- …

## 四、我明确不会做的
- …

## 五、我找到的对标与参考
- <作品/做法> —— 我打算从它身上学什么
```

**每题的写法纪律：**

- 必须给**选项或例子**。"你想要什么风格"这种问法只会得到"好看一点"。
- 必须能回答。问用户"你觉得用什么渲染管线"是错的——那是你的活。
- 有参考图就贴图，或给出可直接搜的关键词。
- 「为什么问」要写清它会影响什么，用户才知道要不要认真答。

## 必须覆盖的提问面

**动笔之前先读这一条：问卷之前必须已经有具体方案和快乐账本。**

每个具体方案必须先写清：玩家为什么玩、哪一个动作让人开心、前 10 秒/60 秒/5 分钟得到什么反馈、用户选择这个方向会改变什么、第一次结束后为什么会回来、这个方案怎样会变无聊。只写“有趣、治愈、爽、很有氛围”不算设计。

零到一任务（用户只给了题材或一句话）在写这份文档之前，`d_state.design_basis` 必须先写出来，且 `design_basis.pitches` 至少要有 **2 条可命名的具体方案**——判据是读得出"这是哪款游戏"，而不是"这是什么品类"：

- ✅「退潮后的滩涂拾荒者」「候鸟迁徙的领航员」
- ❌「一个观赏模拟器」「一个治愈向游戏」——只说出品类，等于没想

用户说"**你多想几个**"时，要的就是 `pitches` 里的东西：**几个具体的游戏**。直接跳到下面的表格开始列问题，就是技能明文禁止的**领域固定问卷**。

宿主会在 `kickoff.status` 变成「已发出」后硬查这一项，缺了每次写状态都会收到模式缺陷。

问题应当**从方案里长出来**：先有"退潮后的滩涂拾荒者"，才会问出"潮汐按不按真实时间走"；没有方案时问出的"时间逻辑"，只是把表格抄了一遍。

| 面 | 典型问题 | 不问的后果 |
|---|---|---|
| 目标与成功标准 | 什么算"做成了"？给你看时你最先看什么？ | 做完才知道方向错了 |
| 用户与场景 | 给谁用、什么设备、什么场合、单次多久 | 交互与体量全错 |
| 核心动作 | 用户/玩家反复做的那一个动作是什么 | 做出来不好玩 |
| 取向光谱 | 硬核↔纯爽 / 应试↔沉浸↔打卡 / 效率优先↔体验优先 | 手感与节奏全错 |
| 内容量级 | 多少关/多少词/多少条目算够，首发要多完整 | 交付"能跑但没内容" |
| **美术权重** | **画面好不好看对这个产品有多重要？S/A/B** | 做出难看的东西 |
| 美术风格 | 有喜欢的作品/风格/颜色吗？有绝对不要的吗（不要 AI 味/不要像素风）？**注意：画风不要用文字选项问——先渲 3 张同场景样图给他挑**（见下） | 风格返工 |
| 音频 | 要不要声音？"有就行"还是"要有感觉"？ | 无声产品或噪音 |
| 平台与分发 | PC/手机/网页；单机/联网；要不要给别人下载 | 打包方式返工 |
| **宿主版本（mod 必问）** | 给哪个宿主版本、哪个加载器做？（例：MC 1.20.1 + Forge / 1.21 + NeoForge / Fabric）**先扫本机再问**，并给出可选项与推荐 | jar 根本装不上 |
| 联机范围（mod 且要联机时） | 几个人玩？自建服务器还是局域网/内网穿透？ | 同步机制与测试方式全错 |
| 数据与存储 | 要保存进度吗？跨设备吗？跨天连续吗？ | 存档结构返工 |
| 时间逻辑 | 依赖系统日期/时区/连续天数吗？ | 跨天逻辑崩 |
| 技术边界 | 能联网吗？能装依赖吗？能花你的钱吗？ | 方案不可用 |
| **预算** | 若用图像 API：单次与累计上限 | 意外花钱 |
| 明确排除 | 你**不要**什么 | 最省事的一题，必须问 |
| 参考作品 | 喜欢的、**以及讨厌的** | 讨厌的往往比喜欢的更有信息量 |

## 红色项处理（V2 硬规则）

**`blocking_count` 必须恒为 0。**

如果你发现某件事"不问清楚就没法动"，那不是项目的问题，是这份文档漏了：

1. 把这类问题**补进文档**（它属于上面哪一面？为什么当初没列？）。
2. 把当初的漏问记进 `d_state.blockers`：`what = 漏问的问题`，`need = 用户补答`。
3. **不要**把运行停在"等用户决定"上。推不动的部分先放下，做不依赖它的部分。

**待决项一律 `level: 黄`。** 出现红色说明模式有缺陷；宿主的自查会在 `d_state` 返回里直接报错要求你补问。

## 超时推进

- 每条黄色项都要写 `fallback`（你推荐的默认值）与 `asked_at`（问出去的时刻），`timeout_min` 缺省 `40`。
- **`asked_at` 只能取自 `d_state` 返回里的「服务器时间」那一项**（`now` 字段）。施工锁生效时你调不到 shell（`pwsh Get-Date` 会被引擎拒绝，这是正确行为），**自己编一个时间戳会让 40 分钟超时判定完全失准**——这是真机上踩过的坑，别重演。每条黄色项**必须有 `fallback`**：没有它，超时推进就没有可推进的目标。
- **`fallback` 必须是你真敢交付的值**，不是占位符——40 分钟后你真的会按它做。
- **`fallback` 不能是需要用户继续参与的分支**，否则超时推进等于把自己锁死。最典型的是美术权重：**Q3 的 fallback 不要写 S**（S 的定义就是"必须等用户给参考或授权"），写 **A 或 B**。这样超时后你能把其余所有事推进下去，美术那一项仍然作为黄色项挂在用户名下等他回来——而不是整条流水线卡在一个你自己选的死结上。
- 超时无回应后按 `fallback` 推进，并写入 `d_state.auto_advance_log`：

```
auto_advance_log: [{ item: "美术风格", default_used: "成套 CC0 像素包 + 统一色相偏移", reason: "标黄项等待超 40 分钟无回应", at: "<ISO 时间>", notified_via: "IM 推送" }]
```

- 然后 `consent` 可记 `{ status: 已确认, basis: 超时推进默认值 }`。**宿主会核对 `auto_advance_log` 里是否真有记录**，凭推测写会被引擎拒绝。
- 通知用户：如果本机装了 IM 推送能力，在发出问题时推一条到手机（`d_state` 的能力自检会告诉你有没有）。没有就说清楚"我不会主动叫你，你回来看文档"。

## 感觉流派翻译法（用户只会讲感觉时）

很多人说不出"我要什么风格"，只会说"我想要那种孤零零的、风很大的感觉"。**感觉不是无效输入，是检索线索。**

**触发条件（别漏了后半句）：** 不只是"用户整段话都在讲感觉"才算。用户**夹在需求里的形容词**同样是感觉输入——"**唯美**""治愈""宏大""压抑""安静""有氛围"——**只要是形容词而不是可判定的规格，就必须走这条路径翻译，不许原样还回去。**

反例就是最典型的那种："有没有唯美的挂机游戏？" → "好的，我会做得唯美一点。" 形容词原样退回，等于没做设计；用户拿到的还是一句形容词，只是换了个说话人。**"唯美"必须变成：哪几张参考图、色板里哪几个色、天空占画面多少、剪影几层、光往哪打。**

1. **原样记下**，不要改写成你的形容词。"他要的是忧郁感"是改写，不要做。
2. **定位**：什么时候、在哪有过这种感觉（哪款游戏 / 哪部电影 / 哪次旅行 / 什么天气什么时间）。
3. **压缩成一张画面或一个动作**："风很大 + 孤零零" = 一个很小的剪影，站在很大很空的渐变天空下。写出来给用户看，让他说"对 / 不对"。
4. **找成熟作品**：谁做过这个感觉（例如 Alto's Odyssey 用渐变天空 + 多层剪影 + 随时间变化的光照表达孤独与辽阔）。**这是研究任务，不是猜。**
5. **抽成可执行元素**：色板（几个色、明度与饱和度范围）、构图（留白比例、剪影层数）、动效（草摆动、云飘、粒子）、音色（长混响、低音量环境音）。
6. 整条路径写进 `d_state.design_basis.feeling`，并在回执里给用户看"感觉 → 画面"的翻译结果。

**反例（不要这样）：** 用户说"要有点治愈感"，你回"好的，我会做得治愈一点"。这是把感觉原样还回去，等于没做设计。

## 画风：渲图给用户挑，不要让他对着文字想象

`art_weight` 是 **S/A** 时，画风/视觉方向**不得以文字选项形式提出**。

给用户一张写着"极简线框 / 剪影渐层 / 程序化噪声"的表格，他只能靠脑补选；脑补出来的和你做出来的几乎一定不是一回事——**这就是返工的开始**。

**做法：**

1. 挑**同一个场景**（例：同一片海岸的黄昏）；
2. 渲 **3 张**不同风格的样图；
3. 直接给图，不给词；用户指哪张，哪张就是风格锚点，写进 `design_basis.feeling` 与 `art.references`。

**渲染样图属于研究动作，不受施工锁限制。** 路径：写静态 `.html` → `vision_html_screenshot` 出 PNG → 拿给用户看。这一步**不建工程、不写产品代码**，在 `consent.status` 还是「未确认」时同样能做——**不要因为"锁着不能动"就退回文字表格**，那正是本条要消灭的行为。

> 这和施工锁不冲突：锁锁的是**改交付物**（`write` / `edit` / 子代理 / 施工命令），不是**做研究**。渲 3 张静态图看风格属于研究，和查对标作品、读文档同一类。

## 收尾检查

- [ ] 文档已落盘，路径真实存在（`d_state.kickoff.path` 指向它）。
- [ ] **`design_basis` 六项非空（含 `feeling`），且 `pitches` 有 ≥2 个可命名方案**（先有方案，才有这份文档）。
- [ ] 每条黄色项都有 `fallback` 和 `asked_at`（时间取自 `d_state` 返回的「服务器时间」）。
- [ ] **每条的 `asked_at` 是照抄服务器时间，不是自己推的**——宿主会拿本机时间比，差太多直接报缺陷。
- [ ] `blocking_count` 为 `"0"`，没有任何红色项。
- [ ] 美术权重 S/A/B 问过了。
- [ ] **美术权重的答案已经写进 `surfaces` 对应板块的 `art_weight`**——不是只问过、只记在正文里。
- [ ] 美术权重是 S/A 时，**已渲 3 张同场景样图**（而不是给了文字选项），并把用户挑的那张写进 `design_basis.feeling` 与 `art.references`。
- [ ] 用户话里的形容词（唯美/治愈/宏大…）已按"感觉流派翻译法"翻译过，没有原样还回去。
- [ ] 「你**不要**什么」问过了。
- [ ] 回执里告诉了用户默认值策略与 40 分钟规则。
