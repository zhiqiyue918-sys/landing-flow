# 落地流 · 施工：唯一主干、完整模块、真实证据

## 先确定最终形态

原则：**先决定最终要做成什么，再决定今天做什么。**

不要默认采用"先随便做一个以后全部推翻的 MVP"。可以暂时减少功能数量，但以下内容应尽量从最终结构反推：模块边界、数据结构、核心接口、状态模型、用户入口、主工程、扩展位置、测试和验收方式。

对每个模块写清：职责、依赖、对外接口、状态、完成标准。

## 唯一 Canonical Source

正式施工后必须存在唯一可继续施工的主工程 / 主版本 / 主源码。实验、候选、checkpoint、历史包可以存在，但不得形成多个长期"最新版"。

技术探针（验证某库能不能工作、某接口能不能调用、性能够不够、某交互能不能实现）允许存在，但探针不是产品版本：成功后必须回收进正式架构，失败则归档或删除。不得留下多个长期并行 prototype，并把其中任何一个误称为正式产品。

## 模块完成标准（全部满足才算 DONE）

1. 已进入唯一主干。
2. 核心逻辑完成。
3. 必要 UI / 用户入口完成。
4. 数据 / 状态完成。
5. 异常与恢复处理完成。
6. 相关测试通过。
7. 与其他模块集成。
8. 至少一条真实使用路径可达。
9. 没有用旁路 Demo 冒充正式能力。

骨架建立后，以"完整模块"为主要施工单位：一个模块开始后，尽量从入口到验收收口，再进入下一个主要模块。避免长期 UI 20% / 数据 30% / 设置 40% / 核心 50% 的状态。

## 编号语义

- Y：原计划步骤。
- X：修复已存在问题。
- Z：新增原计划没有的新工作。
- B：补回原本应该有但遗漏的内容。
- G：调整原方向、顺序、方法或依赖。
- S：删除原计划中的工作。

Y 主线确认后不要因为出现 Bug 就全部重编号。示例：`Y8-X1`（Y8 的第一次修复）、`Y8-B1`（补回 Y8 漏掉的内容）、`Y8-G1`（建议改变 Y8 的实现方向）。

所有 Y/X/Z/B/G/S 项都登记进 `d_state.plan` 与 `d_state.change_items`。

## 变更权限

| 变更 | 权限 |
|---|---|
| 普通 X | 直接执行 |
| 明确漏项 B | 不扩大产品范围时直接补 |
| 小型必要 Z | 登记并执行 |
| 会明显扩大范围/周期/风险的 Z | 先告知用户 |
| G / S | 默认需要用户确认，除非用户已明确要求该改变 |

## 自己拆计划，不频繁打断

用户确认 ConstructionBrief 后，你自己生成内部阶段与施工图，用户不需要逐条发送下一步。禁止：每改一个文件就停；每写一个函数就问"继续吗"；每完成一个小动作就把项目管理责任交回用户；因为需要做内部规划就要求用户重复已经确认的目标。

只有这些情况才真正等用户：新出现的关键产品决策；用户意图存在实质冲突；风险明显提高；不可逆操作；权限缺失；需要用户本人完成外部认证/付费/法律确认；无法通过研究和技术判断可靠继续。

## "代码写完"不等于完成

按项目适用情况自动执行验证：build、test、lint、typecheck、integration test、真实启动、浏览器验证、UI 真实操作、声音/动画/交互体验检查、历史回归、异常路径、存档/恢复/更新等关键链路验证。

把真实执行的命令与结果登记进 `d_state.verification`（`what / command / result / evidence`）。未真实执行的验证不得写成通过。

## 验收分两半，缺一不可

1. **你能自证的一半**：构建、测试、真实路径、数据正确、异常恢复 —— 写进 `verification`。
2. **只有用户说"是"才算过的一半**：面向人的交付必须写出主观验收项（爽不爽、有没有感觉、愿不愿意继续用、画面能不能打动人），写进 `final_acceptance.user_only`，**你不能替它打勾**。没有拿到用户答复之前，状态不得写 `COMPLETE`，回执里要明确说"这一半还等你确认"。

对照检查：如果验收清单里的每一条你都能自己跑完，那说明**验证对象选错了**——自动化的东西进清单，需要人感受的东西永远进不了清单。

## 交付面清单：每个板块都要有形式与证据

美术、音频、内容、领域专业性、数值曲线……每一块都必须先在 `surfaces` 里有归属（能力 / 具体形式 / 来源 / **物料 / 取材路径 / 许可 / 美术权重**），再在交付时给出**该板块自己的证据**：

- 美术：**把实际画面调出来看一眼**（截图 + 你看到的东西 + 你认为哪里还不行），不是"用了 Canvas 绘制"，也**不是**用文字描述代替看。"配色协调、层次清晰"这类句子谁都能写，不构成证据；
- 音频：列出实际存在的声音与触发时机（并说清你听过没有），不是"预留了音频接口"；
- 数值：给出曲线与关键节点的真实数字和来源；
- 内容/领域：给出内容结构，并说明它对照了哪条领域权威做法。

## 自视门：交付前必须真的看一眼（V2）

只要交付里有画面、界面或声音，报"完成 / 通过"之前必须走完这条链：

**真的跑起来 → 截到画面（或用 `vision_*` 工具打开渲染结果）→ 看它 → 把截图路径与判断写进 `verification`。**

- **没有"看"这一步就不是完成。** 写得出颜色值、看得到代码，都不等于看过画面。
- **没有视觉能力时**（`d_state` 的能力自检会告诉你）：不得声称看过，不得把美术/界面类板块标记为已验证；如实告诉用户这个限制，并把"需要视觉能力"记进 `blockers`。用户侧的开关是输入框的 **「👁 识图」**。
- 固定要查的几处：文字错字/糊字、手指与肢体、透视、物体数量与位置、中英文混排、**与用户参考图的风格是否一致**、以及动效是否卡顿。

### 证据帧必须等于实机（V4，比上面几条都重要）

**审视用的截图，必须来自用户会打开的同一条路径**：同一个文件、同一段代码、同一种进入方式（同一 URL、同一入口、同一套参数）。

实测教训值得记住：一次交付里，成品自己另写了一个渲染脚本导出"证据帧"，那些帧**比实机亮得多、层次清楚得多**——于是它拿美化过的帧给自己判了通过；用户双击打开实机，看到的是更暗更糊的版本。**用美化的帧当验收证据，比没有证据更糟**，因为它会把真问题掩盖在"证据"底下。

自检问句：**"我这张图，用户双击打开能看到一模一样的东西吗？"** 答不上来，它就不是证据。渲染脚本与用户入口不一致时，以用户入口为准去截。

## 体验官审阅门：交付给用户之前（V2）

**用户是最终验收者，不是第一个体验者。** 可运行的成品做完之后，先把 `deep-construction-review` 加载起来，按产品类型选体验官（初见官 / 核心循环官 / 留存官 / 学习官 / 可用性官 / 对抗官），每位用**独立子代理**跑一遍，结果写进 `d_state.reviewers`。

- 全部通过（或退回重修后再通过）才允许交给用户。
- 体验官的"不通过"属于**业务失败**：回 DESIGN / BUILD 修，记进 `repair_history`，修完换新子代理重跑。
- 非独立子代理的"通过"不算证据——宿主的自查会直接判为橡皮图章并报错。

弱项板块若没有"用户提供参考"或"用户明确说随便你"，**不许进入 BUILD**；把它无声地做成占位品再当成正式方案交付，视为违反本模式：用户有权知道"你得到的这个形式是什么"，而不是事后发现"原来只是代码画的剪影"。

## 游戏专项体验门

游戏或可玩交互项目必须补全 `d_state.gameplay_review` 与 `visual_review`，且宿主会在 `ACCEPTANCE / COMPLETE` 硬拦缺项：

- `gameplay_review`：真实运行入口与玩家输入路径；三轮核心循环的动作/决策/反馈/结果观察；不同选择的结果对照（或线性设计的有效变化）；失败重开路径（如适用）；具体重玩理由。
- `visual_review`：用户真实入口的截图；首屏目标/主操作/HUD 层级结论；具体 UI 缺陷；根据截图发现做过的改动；同入口复测结果。

游戏要加载 `deep-construction-reviewer-core-loop`、`deep-construction-reviewer-usability` 和 `deep-construction-art`；视产品形态再加初见官/留存官。试玩官不得只读源码与设计文档，必须启动用户可运行版本、按真实输入路径操作并留下可复现证据。核心循环找不到具体重玩理由，回 DESIGN 重做，不以加粒子或加内容交差。没有视觉能力时标未验证并把实机截图交给用户判断，不能自评通过。

## 产品级完成门

最终 PASS 同时要求：模块正确 + 真实产品可用 + **体验官全部通过** + **主观验收项已由用户确认**，并且至少存在一条真实用户完整路径。

**默认级别：GitHub 可上架级。** 别人照你写的自述能跑起来、内容量真实、没有占位品、没有死文件、核心路径完整。自述至少回答：这是什么、给谁用、怎么跑起来、现在能做什么、还不做什么。

**宿主游戏 mod 的完成门（V5）："能跑起来"必须带上主体。** mod 不是独立产物，它的运行环境是**特定版本的宿主游戏 + 特定加载器**。所以自述里的"怎么跑起来"不能只写"双击"或"装进游戏"，必须写清这一组：

> 装了 **Minecraft 1.20.1 + Forge 47.2.0** 的玩家，把 `xxx.jar` 放进 `.minecraft/mods/`，启动游戏，进世界后 **看到什么**。

少了宿主版本与加载器，验收**根本无法执行**——版本不对 jar 连加载都不会加载，而"我这边是好的"证明不了任何事。宿主会在 ACCEPTANCE / COMPLETE 阶段硬查这一组信息（`platform.host_*` 与 `final_acceptance.user_path`），缺了直接判缺陷。

同理，**联机部分的验证不能只用单机测**：分得清服务端/客户端逻辑、找第二个人（或开一个专用服务器）实际连一次，才算走过那条路径。

**工程形态检查（交付前必做）**：新增文件/目录是否都服务某个已列出的板块？有没有空壳文件、脚手架残留、实验残留、重复实现？文件树能不能被一句话解释？**文件膨胀本身就是缺陷**，不是"工程规范"——"产生了大量没有意义的文件"属于应当被拦下的失败。

以下都不算完成：有核心能力但用户没有入口；有漂亮 UI 但没有真实能力；测试文件存在但没真正跑；Agent 自述"应该没问题"；测试全绿但没人玩过/用过；内容量明显撑不起宣称的体验；文件一堆但说不清各自为什么存在。

## 向用户汇报的关键词

- 完成了什么：只说真实完成项，附证据形式（命令、测试数、可运行入口）。
- 用了什么 + 为什么：一句话级别。
- 还剩什么：未完成、阻塞、等待用户决定。
- 下一步：你自己将要做什么。
