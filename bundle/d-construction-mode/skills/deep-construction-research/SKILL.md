# 落地流 · 外部现实侦察与技术决策

研究不是失败后的补救，是施工前的默认动作。目的不是写研究报告，而是先搞清楚现实世界现在怎么做。

## 何时研究

- Greenfield / 新模块：在完成初步目标理解与专业模块识别后尽早研究，再决定该问用户哪些问题。
- 已有项目 / Bug / 改造：先读取足够的现有技术栈与真实问题，再针对相关模块调查当前成熟做法；不脱离现状做无关泛搜。

## 研究的八个必答问题

1. 现在行业主流怎么做？
2. 官方推荐怎么做？
3. 有哪些成熟技术和现成能力？
4. 哪些方案仍在维护（最近提交、版本节奏、issue 响应）？
5. 哪些方案已经过时？
6. 常见失败模式是什么（已知坑、迁移史、破坏性变更）？
7. 真实成本、限制与兼容性如何（许可证、平台、性能、体积、学习成本）？
8. 哪些东西根本没有必要自己造？

## 承载平台侦察（第 0 层，别漏掉）

八个问题都是**在选定承载平台之后**才有意义的。所以先补这一步：**这件作品整体靠什么做出来？** 漏掉这一层，你会把"选哪个库"研究得很细，却从没问过"是不是有个引擎能把这个游戏整个做出来"——真实教训见 `deep-construction-reuse`。

至少查清：

1. 这个品类的成熟作品**是用什么做的**？（看它们的官方说明、导出格式、工程结构；这一步往往直接给出答案）
1.5 **先扫本机已经装了什么**（`Get-Command` / 常见安装位 / `tools\` 目录 / 用户以前的工程目录）——本机已有 Godot 4.7（`Y:\codex\墨劫行\tools\godot\`）等引擎时，不要以"要下载"为由否决它；以前的游戏工程里常带着可复用的引擎、导出模板与素材。
2. 有哪些成熟引擎/框架/平台可承载它？各自**导出目标**是什么？
3. 它们的**许可与费用**：可否商用、有无收入门槛或分成、导出到某目标是否收费。
4. **包体与运行时**：引擎本体的体积、是否需要服务器、能否离线、能否单文件交付。
5. **它能替你做掉哪些原本要手写的东西**（物理/渲染/动画/粒子/UI/输入/存档/本地化/寻路）。
6. 还有**无代码/低代码制作平台**（Construct、GameMaker 的可视化路线、RPG Maker 等）是否也够用——尤其当用户不是程序员时。
7. 这些平台的**维护状态**（最近提交、版本节奏、社区规模）。

结论写进 `d_state.platform`（`choice / kind / alternatives[{name, why_not}] / licence / cost / export_targets / note`），并作为一条 `d_state.decisions` 记录。**进入 DESIGN 之后 `platform.choice` 不得为空**——宿主会把它当模式缺陷报出来。

## 品类、体验与领域层（面向人的交付为硬门）

只要交付是面向人的产品（游戏、学英语这类学习产品、内容产品、效率工具、界面），上面八个问题**只覆盖了技术层**。必须再补两层，三层都做完才算完成侦察：

**A. 品类与用户层**（人为什么用、成熟产品长什么样）

1. **目标用户与场景**：谁、在什么情况下用、用多久、替代品是什么（包括"什么都不用"）。
2. **这个品类的成熟产品怎么做**：挑 3–5 个成熟作品，看它们的核心循环、节奏曲线、留存钩子、内容/功能组织方式。
3. **人为什么用 / 为什么玩**：动机来自哪里（成长感、掌控感、收集、表达、社交、实用性……），写清本产品押的是哪一条。
4. **常见差评与流失点**：搜真实用户负评与抱怨，列出"千万别做成这样"的清单。
5. **视听与交互惯例**：这类产品画面上常驻什么、操作反馈怎么做（数字/动效/音效/震动/文案），有哪些低成本做出"有感觉"的成熟套路。

**B. 领域与专业层**（这个领域本身怎么做才对）

6. **领域权威实践**：这个领域有没有公认的方法论、标准或研究结论，必须被遵守或至少被解释。
   - 学习类产品举例：二语习得研究、间隔重复与遗忘曲线、CEFR/词汇量分级、听说读写的训练配比、纠错反馈方式；
   - 效率工具举例：既有工作流惯例、快捷键与无障碍规范、数据导入导出与隐私合规；
   - 内容产品举例：内容分级与选题结构、更新节奏与质量下限。
7. **合规与伦理底线**：涉及未成年人、健康、金钱、隐私、成瘾设计时，先查底线再设计。

要求与判定：

- 来源必须真实读过并记进 `d_state.benchmarks`（`{ work, what, source }`），差评与惯例、领域结论同样要记。
- **技术层研究不能替代这两层**：只做了技术与选型研究时，`research.status` 不得写"已完成"，也不能进入 Brief 确认。
- 停止条件：已有 3–5 个对标产品、清楚人为什么用、有差评清单、有视听惯例结论、有领域权威结论 → 停止，不要扩张成行业研究报告。
- 触发时机：Greenfield 或新品类，在**问用户高影响问题之前**或同时进行——否则你会用技术问题掩盖设计问题，也会问出用户本来不需要回答的问题。

## 来源优先级

1. 官方文档 / 官方推荐路径。
2. 正式标准、协议或平台规范。
3. 持续维护的成熟开源项目及其官方文档。
4. 成熟行业实践与高质量技术资料。
5. 高价值社区经验（用于发现坑点与真实体验）。
6. 零散教程只作补充，不作为唯一依据。

对快速变化的技术生态，技术选择不得只依赖模型记忆；必须核对当前版本与维护状态。记录实际读取过的来源（`d_state.research.sources_used`）。

## 停止条件

已经找到足够可靠的实现路线、主要替代方案、关键风险与限制、足以做当前技术决定的证据 → 立刻回到设计/施工主链。禁止 Research → Research → Research 无限扩张。

## Technical Decision Record

重要技术选择内部记录到 `d_state.decisions`：

```
decision_id：D-001
选择：<采用了什么>
用途：<承担什么职责>
选择原因：<基于证据的理由>
主要替代方案：<候选列表>
未采用原因：<逐个说明>
外部依据：<官方文档/标准/仓库/版本>
对产品的影响：<体验/成本/平台/隐私/扩展>
状态：ACTIVE | SUPERSEDED | EXPERIMENTAL
日期：<YYYY-MM-DD>
```

## 判断"是否需要交给用户"

以下取舍必须翻译成人能判断的语言再让用户决定：用户体验、平台覆盖、是否需要服务器、长期费用、数据所有权/隐私、商业许可、发布渠道、后续扩展方向、不可逆迁移成本。

## 用户回执格式（默认简版）

```
采用：XXX
用途：XXX
原因：XXX
```

必要时增加：`没有采用：YYY；原因：ZZZ。` 不要默认向用户输出长篇技术论文。用户需要时可展开完整决策记录。

## 常见错误

- 跳过研究直接按模型记忆选型。
- 只找一个方案就下结论，没有替代方案对比。
- **只研究库、不研究承载平台**：把库选型做得再细，也补不上"整体从零手写"这个错误。游戏/交互类必须先查引擎与制作平台。
- 研究到"看起来不错"就停，未核对维护状态与许可证。
- 把研究写成论文给用户，而没落到决策与施工。
- 用外部方案覆盖用户已明确的产品意图。
