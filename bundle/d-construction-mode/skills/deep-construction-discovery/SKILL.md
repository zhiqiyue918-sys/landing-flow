# 落地流 · 需求发现（DISCOVERY）

## 何时用

- 新的任务或明显转向的新需求。
- 只有当前对话 / 只有资料 / 一句话 Greenfield 的开局。
- 已有项目但产品目标不明确，或用户中途修改了产品要求。

目标：在进入正式 DESIGN / BUILD 之前，把「最终应该做成什么」确定到可施工的程度。高细度 ≠ 无限询问。

## 第一步：分类现有信息

先建立五类清单（写进 `d_state`）：

| 类别 | 含义 | 处理 |
|---|---|---|
| KNOWN | 已明确、有来源 | 直接采用，不再询问 |
| UNKNOWN | 尚未明确且可能影响结果 | 判断是否值得询问 |
| ASSUMPTION | 你当前推断 | 标记为推断，可被更高等级真相推翻 |
| DELEGATED | 用户明确委托你决定 | 你自己决定，只回执结果 |
| DEFER | 现在不必决定、不阻塞当前阶段 | 明确延期，不硬猜 |

资料与仓库优先于询问：能从文档、代码、运行结果读出来的，不要问用户。

## 第二步：识别专业模块

从任务语义推出完成产品需要的专业模块、底层技术、依赖条件、工具/素材、模块关系、实现难度、可靠实现路径、需要先做实验的未知项。不得做到一半才发现关键能力从未考虑过。

对每个模块记录：`名称 / 作用 / 成熟方案候选 / 未知项 / 是否需要技术探针`。

## 第三步：动态生成问题

问题生成链必须逐级走完，不得跳步：

1. 当前表达：用户到底说了什么。
2. 任务语义：这实际是什么类型的任务。
3. 所需专业模块：上一步得到的模块清单。
4. 当前缺口：哪些模块缺少决定性信息。
5. 影响判断：这个缺口会不会改变产品形态、核心体验、主要业务逻辑、平台、数据与隐私、成本、不可逆风险、主观偏好、验收标准、总体架构。
6. 是否值得询问：不值得的转 AUTO DECIDE / RESEARCH / DEFER。

禁止：识别到"游戏"就加载固定问卷；用户已说"2D 纯跑酷、无战斗"还问攻击方式；问资料里写清楚的问题；为显得专业而问用户根本不需要决定的工程细节。领域模板只能当候选问题池，不能当必问清单。

## 第四步：分级

- HARD UNKNOWN｜必须问：答案会明显改变产品形态、核心体验、主要玩法/业务逻辑、平台、重要数据与隐私、明显成本、不可逆风险、用户主观偏好、验收标准或总体架构。
- RECOMMEND｜先建议再确认：存在明显较优默认路线，但用户可能有偏好。格式：`建议：XXX。原因：XXX。没有特别要求我就按这个方向做。`
- AUTO DECIDE｜自己决定：低风险、容易修改、不改变主要体验与架构的实施细节。
- DEFER｜延期：现在没有足够证据，且不阻塞当前设计与施工。

## 第五步：选择询问模式（默认「一次问全」）

**默认是集中模式：一次把属于用户的问题全问完，让用户一次答完，然后你自主跑到底。**

- 用户不反对被提问；用户反对的是"每一轮都要他回答"——那等于要求他一直坐在电脑前，模式就没有意义。
- 因此顺序是：先把外部现实侦察做完（品类/体验/领域层，见 research 技能）→ 再按下面的清单一次问全 → 用户一次答完 → 记录 `d_state.intake = { status: 已回答, autonomy: 已授权 }` → 之后不再为同类问题开口。
- 自然模式（分批问）只在两种情况下用：用户明确要求分批；或某个决策确实依赖上一轮答案、且无法事先预算出可选分支。

### 一次问全清单（逐条过，不需要问的写明来源）

0. **先给出零到一前置设计包和快乐账本草案**（定义 / 核心快乐与动机 / 快乐证据 / 选择影响 / 对用户的意义 / 产品结构分解 / 时间与状态逻辑，写进 `design_basis`），再据此提问——问题从具体方案和快乐账本里长出来，而不是凭空列清单。

   **这一条是硬顺序，宿主会查**：`d_state.kickoff.status` 一旦写成「已发出」，`design_basis` 的六项（含 `feeling`）必须非空，且 `design_basis.pitches` 至少要有 **2 条可命名**的具体方案，否则每次写状态都会收到模式缺陷。判据是**命名粒度，不是方案数量**：

   - ✅「退潮后的滩涂拾荒者」「候鸟迁徙的领航员」——读得出**这是哪款游戏**；
   - ❌「一个观赏模拟器」「一个治愈向游戏」——只读得出**这是什么品类**，等于没想。

   用户说"**你多想几个**"时，他要的就是 `pitches` 里的东西：几个具体的游戏。给他一份问卷是把"多想几个"退回给他自己。
1. 目标用户与使用场景（谁、什么时候用、用多久、替代品是什么）；
2. 核心价值与动机（人为什么用/为什么玩，押的是哪一条动机）；
3. **取向选择**：该品类的取向光谱与本次选择（肉鸽：硬核 ↔ 纯爽；学习：应试 ↔ 沉浸 ↔ 打卡；工具：效率 ↔ 体验）；
4. 内容或能力边界（做到什么程度算够；首版范围上限）；
5. **内容侧逐项取舍**：把候选内容项列全让用户勾（学习类例：单词 / 短语 / 文章 / 听力 / 阅读 / 写作 / 口语 / 语法；游戏类例：关卡 / 装备 / 敌人 / 成就 / 排行），**明确哪些要、哪些不要**；
6. 交互与 UI 取向（要信息密度还是干净？哪些功能收起、哪些常驻？）；
7. 平台、形态与分发（网页/桌面/移动；是否要安装、是否联网）；
8. 风格、参考物及参考层级（参考哪一层：玩法/数值/视觉/交互/架构）；
9. 现实约束（时间、预算、隐私、合规、离线、目标设备）；
10. **时间与状态逻辑**：是否需要系统日期/跨天/连续天数/复习或刷新节奏；出现异常时（改系统时间、跨时区、久未打开）你希望怎么处理；
11. 明确不做（防止后期范围膨胀）；
12. **验收标准，含只有用户能判定的主观项**（"什么算做好了""什么算不好玩/不好用"）；
13. **交付面清单的素材与参考**：逐块问"有没有参考图/素材/文案/资料/想要的方向"——玩法、数值、美术、音频、内容、领域专业性。**你自己不会做的板块，必须在这里问**：要么拿到参考或素材，要么拿到"随便你"的明确授权。板块整体空白就动手 = 严重违规。
14. **美术权重 S/A/B**：画面好不好看对这个产品有多重要？（S=画面就是卖点，必须等用户；A=重要但可超时推进；B=画面不重要）
15. 长期方向与更新节奏（一次性交付，还是之后持续追加内容）；交付级别（本次要做到"能自己玩/自己用"，还是"可以公开给别人用"）。

问题可以多，但要**结构化**：分组、给推荐项、每题一句话说明影响；宁可一次 16 组，也不要分成 16 轮。

### 什么该问、什么不该问：「品味题」与「规格题」

三条铁律：

| 类型 | 例子 | 处理 |
|---|---|---|
| **品味题**｜只有用户知道答案，而且他能**看着判断** | 画风、配色、构图、角色观感 | **禁止用文字问。** 先渲染样图给他看（见下） |
| **规格题**｜答案会改变产品形态，只有用户有立场 | 要不要存档、单机还是联网、灾难强度、时长与节奏、**mod 打给哪个宿主版本** | **必须问**，一次问完 |
| **施工题**｜低风险、易改、不改变主要体验 | 引擎选型、目录结构、参数取值、库里用哪个 | **自己决定**（AUTO DECIDE），只回执 |

**不要把施工题反问用户**（那是你的活），**也不要把品味题丢回用户**（那是没做设计）。

### 规格题的典型：「给哪个版本的宿主做」

做 mod 时最容易犯的错，是**替用户把版本定了**——"最新版最好"、"1.21 比较新"、"1.20.1 资料多"。这些都不成立，因为：

- 版本和加载器**是绑死的**（1.20.1 上 Forge 生态成熟；1.21+ NeoForge 是主线；Fabric 自成一套）；
- **用户的朋友装的是哪个版本，只有用户知道**——这不是技术判断，是事实性问题；
- 判错了不是"不太好"，是**做出来的 jar 根本不会被载入**。

所以这条必须问，而且要**给出可选项和推荐**，而不是空问一句"你要哪个版本"：

> 你打算给哪个版本做？我看到的选项：
> - **A：1.20.1 + Forge**——资料最多、整合包生态最成熟（我扫到你本机整合包就是这一套）
> - **B：1.21+ + NeoForge**——较新，Forge 的后续主线
> - **C：Fabric**——轻量、更新快，但和 Forge 系 mod 不能混装
>
> 为什么问：版本与加载器决定 jar 能不能被载入，判错了做出来也装不上。
> 我的推荐默认值：跟**你朋友那边实际在用的**保持一致——先确认这个，我再定。

**先扫本机再问**：`.minecraft/versions`、整合包 `mods/` 里的 jar 名（常带 `1.20.1-forge` 字样）、启动器目录。能从环境读出来的事实不要拿去问用户。

### 品味题必须先渲样图，不许让用户对着文字想象

`art_weight` 为 **S/A** 的板块，画风/视觉方向**不得以文字选项形式提出**。

用户回答"你更喜欢哪种画风"时，如果给他的是一张写着"极简线框 / 剪影渐层 / 程序化噪声"的表格，他只能靠脑补选——而脑补出来的和你做出来的几乎一定不是一回事，这就是返工的开始。

正确做法：

1. 挑**同一个场景**（例如"同一片海岸的黄昏"）出 **3 张**不同风格的样图；
2. 直接给用户看图，不是给词；
3. 用户指一张，那张就是风格锚点，写进 `design_basis` 与 `art.references`。

**渲染样图属于研究动作，不受施工锁限制。** 具体路径：写静态 `.html` → `vision_html_screenshot` 出 PNG → 给用户看。这一步**不建工程、不写产品代码**，用的是渲染与看图工具，在 `consent.status` 还是「未确认」时同样可以做——**不要因为"锁着不能动"就退回文字表格**，那正是本条要消灭的行为。

> 例（美术）："美术你有没有参考图或想要的风格？没有的话我按 X 形式做（成套 CC0 像素包 / 极简线框 + 固定色板 / GLSL 程序化背景…），你接受哪种？"——只有用户答"随便你/都行"之后，才把该板块记成 `source: 已授权自主` 并自主决定。

## 交付形态：开工文档（Kickoff Dossier，V2）

**「一次问全」不是聊天里问一长串，而是一份真实文件。** 加载技能 `deep-construction-kickoff`，生成 `<项目>/开工文档.md`，并在回执里给出路径。

- 每条问题都带**为什么问 / 推荐默认值 / 你不回我会怎么做**。
- 每条都写 `level: 黄` 和 `fallback`（你真敢交付的默认值），`asked_at` + `timeout_min: "40"`。
- 写 `d_state.kickoff = { status: 已发出, path, question_count, blocking_count: "0" }`。
- **`blocking_count` 必须恒为 0**：需要阻塞才能问清的问题，说明这份文档漏了——补进去，把漏问记进 `blockers`，而不是把运行停下。
- 用户答完后：`kickoff.status = 已回答`，`intake = { status: 已回答, autonomy: 已授权 }`，此后按自主契约推进。
- 40 分钟无回应：按 `fallback` 推进，写进 `auto_advance_log`，`consent.basis` 可记「超时推进默认值」（宿主会核对留痕）。
- **验收不在超时推进范围内**：产品好不好、爽不爽，只有用户说了算，永远不能靠超时通过。

## 第六步：停止条件与自主契约

以下内容稳定即可停止 DISCOVERY：最终目标、产品形态、核心体验/核心业务、主要使用场景、必须能力、明确不做、关键约束、重要主观偏好、关键风险、验收标准。其余：能自己决定 → AUTO DECIDE；能研究解决 → RESEARCH；可以以后决定 → DEFER。

**自主契约**：用户答完一次问全之后，你在该范围内获得自主推进授权——
- 没问到的：AUTO DECIDE 决定，写进 `assumptions`，继续；
- 不确认也能改的：按 RECOMMEND 先做后报；
- **禁止**为同一类问题发起第二轮询问；禁止"每完成一个模块就来确认一次"；
- 只有出现真正例外才重新开口（关键产品决策变化、意图冲突、风险显著上升、不可逆操作、权限缺失、需用户本人完成的认证/付费/法律动作），且要一次把新问题问完。

## 施工锁：沉默不是授权（引擎强制）

`d_state.consent.status` 默认「未确认」。未确认期间，引擎会**拒绝** `write` / `edit` / `pwsh` / `run_code` / `subagent` / `subagent_fork` / `workflow`：你写不了文件、起不了子代理，被拒时返回说明。研究、只读检查、提问不受限制。

解锁只有三条真依据（写进 `basis`）：

| basis | 何时可用 |
|---|---|
| `用户回答` | 用户本人回答了你的一次问全 |
| `用户授权默认值` | 用户明确说过"按你的默认做 / 随便你 / 你决定" |
| `用户原始需求已完整` | 最初的请求本身已含完整设计与验收标准，并明确要求直接实施 |

**以下都不是授权**：用户没回答；"他可能不耐烦了"；"他应该只想看个雏形"；"我问过了等于他默认同意"；"自主续跑又轮到我了"；"提问通道不可用，先按我的默认做"。沉默时唯一正确的动作是：把问题、推荐默认值与影响写进回执与 `d_state.pending_user_decisions`，结束本轮，等用户回答。硬闯只会拿到一条拒绝，不会拿到文件。

## ConstructionBrief 模板

收敛后写进 `d_state.construction_brief`，并向用户展示可读版本：

```
# ConstructionBrief｜<项目名>
最终目标：<一句话>
使用者 / 场景：<谁在什么情况下用>
最终产品形态：<形态与平台>
核心体验 / 核心业务：<最重要的那件事>
必须能力：<列表>
明确不做：<列表>
平台与环境：<运行环境、依赖>
用户主观偏好：<审美、风格、手感等>
参考物及参考层级：<参考 A 的哪一层>
技术与现实约束：<时间/成本/离线/权限等>
已授权你自行决定：<DELEGATED 列表>
DEFER 项：<延期清单>
主要风险：<列表>
验收标准：<可判定的完成条件；必须含"只有用户说'是'才算过"的主观项>
当前输入来源：<对话/资料/仓库/运行结果>
```

## 体验契约（面向人的交付：Brief 通过前的硬门）

面向人的体验型产品，Brief 里除了上面这些，还必须在 `d_state.experience_contract` 写出**动作级**剧本。写不出具体动作，就是设计没做完——**不得进入 DESIGN / BUILD**，也不得把 Brief 当作可确认：

```
前 10 秒：玩家/用户做什么动作 → 看到什么变化
前 60 秒：会得到几次"变强了 / 爽了"，分别由什么触发
前 5 分钟：目标链（现在做什么 → 为了什么 → 解锁什么）
常驻画面：屏幕上一直有什么；什么数字 / 形状 / 状态在变
每次操作的声画反馈：按下去发生什么（视觉 + 声音 + 数字）
```

判定要求：

- **动作级，不是氛围级**："紧张的氛围""独特的张力"这类句子不算；要能写成"按 X → Y 在 Z 毫秒内变化 → 数字 +N → 声音变化"。
- 核心动作必须是**正反馈为主**；如果核心机制是负反馈（惩罚、损失、张力、倒计时压力），必须单独回答：玩家获得快乐的那一环在哪里？回答不了就不许把它当核心。
- 这五项必须由**用户确认**（或明确说"按你的默认做"）。用户没回答时**不要停在 WAITING_USER_DECISION 干等**：把它写进开工文档的黄色项（带 `fallback` 与 `asked_at`），40 分钟后按 `fallback` 推进并留痕；验收项仍然只有用户能判。
- 同时写 `surfaces`（交付面清单）：玩法与操作 / 数值与曲线 / 美术与视觉 / 音频与声音 / 内容与文案 / 领域专业性 / 平台与性能，逐块写「能力（强/一般/弱/无）+ 本次具体形式 + 来源（对标/自产/用户提供/已授权自主）+ **物料 material + 取材路径 origin + 许可 licence + 美术权重 art_weight**」。**弱项或不会做的板块，来源必须是"用户提供"或"已授权自主"**，否则不许进入 BUILD——不许无声地做成占位品再当方案交付。取材顺序与许可红线见技能 `deep-construction-assets`。

## 确认方式

- 面向用户必须可读、紧凑，不塞内部技术细节。
- 用户确认产品目标后才进入正式 DESIGN / BUILD。
- 低风险实现细节不需要逐项确认。
- 用户答复若改变了产品目标，回到第三步重新判断缺口，不要带着旧结论继续施工。

## 常见错误

- 把"一句话需求"直接当成施工许可。
