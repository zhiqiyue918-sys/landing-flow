# D｜深度施工模式 · A–H 验收测试协议

两条等价路径，任选其一：

- **人工路径（本文件）**：你自己在 GUI 里新建会话、粘贴下面的块。适合你想亲眼看着 D 工作。
- **自动路径（`acceptance/runner`）**：一个临时装置用 Harness 客户端本来就有的 RPC 自己建会话、
  按脚本提交用户回合、读取投影并留下报告；只需**重启一次** Harness，之后无需交互。
  第一轮只跑 2 个回合（Greenfield 开场 + 偏好补充并要求先出 Brief，不施工）。

本文件是**给人执行**的验收脚本：每个测试都要求真实会话、真实输入、真实结果。
构造者（创造模式会话）在测试后从**会话日志 + 工作区产物**读取证据，不采信自述。

## 前置（必须做）

1. **重启 DeepSeek Harness**（完全退出再打开）。插件安装/更新后需要一次重启，重启后跑到的才是最终代码。
2. 重启后回到本会话继续（我这边会接着处理证据与报告）。
3. 三个测试会话都是：**新建会话 → 在预设选择器里选「D｜深度施工模式」→ 按顺序粘贴下面的块**。
   如果预设列表里没有「D｜深度施工模式」，或新建会话报错，把界面原文发我。

## 会话 1｜测试 A（一句话 Greenfield）+ 测试 G（全链可视化）+ 测试 E（成熟底座 / 原创核心）

**块 1-1**

```
帮我做一个小游戏。
```

观察（测试 A 判定点）：不得直接开工；应先识别产品领域与所需专业模块，并做外部现实侦察；
问题要按语义动态生成，而不是固定问卷；能区分"必须问 / 你先建议 / 你自己决定 / 以后再说"。

**块 1-2**

```
补充偏好与边界。本会话同时是「D｜深度施工模式」的验收测试，请严格按 D 模式流程走：
- 类型：2D 像素风，单机小游戏，Windows 桌面优先，能双击打开或一条命令启动即可。
- 玩法：一个能玩通的小关卡：左右移动 + 跳跃 + 收集 3 个金币 + 到达终点。
- 不做：联网、排行榜、存档、多关卡、战斗、手柄、手机端。
- 美术：画面本身不是这个产品的卖点（美术权重 B）——不要用纯色方块糊过去，请按你的取材策略来（成套 CC0 素材包优先，其次能靠图标+排版+色板解决的就不引素材）；选了什么、许可是什么、为什么，告诉我。风格我不管，你决定。
- 技术栈你定，不用问我。
- 复用 vs 原创：请明确告诉我哪些部分采用成熟方案、哪些是本项目原创核心。
- 范围上限：做到「可运行 + 一条真实路径（启动 → 操作 → 收集 3 个金币 → 到终点）验证通过」就停下汇报，不要继续扩展。
- 验收标准：我能在本机启动它，用键盘完成上述路径，并且你给出真实运行/测试证据。
- 每一步之后更新全链状态：输入框上方的 Pipeline 条应显示当前阶段与模块进度，展开能看到阶段、模块、技术决策、验证、Repair、阻塞。
```

**块 1-3**（收到 ConstructionBrief 之后）

```
确认这个 ConstructionBrief，按它开工。做到范围上限就停下汇报。
```

观察（测试 G 判定点）：Pipeline 条应按真实进展变化；技术方案能看到"采用什么 + 为什么"；
模块状态、验证结果、Repair 进展可见；不出现无法解释的百分比；不出现隐藏推理过程。

**游戏专项完成门**：真实游戏项目申请 ACCEPTANCE/COMPLETE 时，宿主必须拦截缺少试玩或视觉/UI证据的完成声明。至少写入实际运行入口、三轮核心循环观察、选择结果对照、失败恢复/不适用依据、重玩理由；以及实机截图、首屏层级、具体视觉/UI问题、修复与同入口复测。非游戏项目不能受该门误伤。

**块 2-1**

```
（没有仓库，没有其它资料，下面是全部输入。）

我要一个「本地文件批量整理」命令行工具，帮我做出来。
- 用途：把下载文件夹里乱七八糟的文件按类型和日期归档到子目录。
- 使用者：我自己，Windows 11，已有 Node 环境。
- 必须能力：dry-run 预览、按扩展名分类、按年月归档、冲突自动改名、生成一次操作日志。
- 明确不做：删除文件、联网、GUI、守护进程、云同步。
- 平台：Windows 优先，命令行使用。
- 偏好：输出简洁可读；默认 dry-run，必须显式 --apply 才真的移动。
- 风险：不要让我丢文件。
- 验收：给我一个可运行的 CLI；在样例目录上 dry-run 输出正确，--apply 后真实移动且日志可查。

```

观察（测试 B/D 判定点）：不得重复询问上面已经写清的信息（技术栈、平台、必须能力、明确不做…）；
必须先理解资料；只补真正高影响的缺口；普通技术选型由 D 研究后自己决定；
D 需要**自己创建项目目录**（没有仓库不能阻塞）；汇报要给出"用了什么 + 为什么"。

**块 2-2**（收到 ConstructionBrief 之后）

```
确认，开工。做到「CLI 可运行 + 在样例目录上 dry-run 与 --apply 都真实跑通」就停下汇报。
```

夹具：`acceptance/fixture-ledger`（真实可运行项目，当前 10 个测试中 4 个失败，含三类不同缺陷）。

**块 3-1**

```
这是一个已有项目：C:\Users\月之七\Documents\deepseek-harness\default-workspace\acceptance\fixture-ledger
它现在有失败的测试。请按 D 模式处理：先读真实现状（技术栈、目录结构、运行方式、真实测试结果），
针对相关模块做必要的外部现实侦察，补齐关键需求缺口，给出 ConstructionBrief 让我确认。
先不要改代码。
```

观察（测试 C 判定点）：读真实现状 → 识别技术栈（Node ESM + node:test）→ 针对性研究而不是泛搜 →
补关键需求缺口 → ConstructionBrief；不得一边看着现有代码一边问"你想用什么技术"。

**块 3-2**

```
确认，开始修到全部测试通过。用 Progress-aware Repair：每一轮记下"解决了什么 / 测试数字变化 / 判定（PROGRESS / INFO_GAIN / STALLED / REGRESSION）/ 下一步"。
```

观察（测试 F 判定点）：不因"第 2 轮"机械停止；判定有真实依据；真停滞时进入 ROOT_CAUSE_REPLAN 并换策略；
只有换策略后仍无结果才 BLOCK。

**块 3-3**（全部测试通过之后）

```
请审计当前实现。
```

观察（测试 H 判定点）：AUDIT → ISSUE QUEUE → BUILD；发现问题后进入可执行修复队列并继续施工，
而不是 AUDIT → AUDIT → ANALYZE 无限循环（除非我明确说"只检查，不修改"）。

## 会话 4｜V2 验收：开工文档 / 不该有红色 / 素材策略 / 体验官 / 能力自检

V2 的六条机制各有独立的判定点。**这一组必须在 GUI 里真实跑**，因为它们测的是"人看不到的地方有没有偷偷放水"。

### 4-1｜开工文档门

```
我要做一个「每天背 10 个单词」的小软件，帮我做出来。
```

观察：
- 不得直接开工。必须先产出一份**真实文件**（`开工文档.md` 或 `docs/开工文档.md`），回执里给出路径。
- 文档里每条问题都有**选项 + 为什么问 + 推荐默认值 + 你不回我会怎么做**。
- `d_state.kickoff.blocking_count` 为 `"0"`，**没有任何红色项**。
- Pipeline View 里出现「开工文档」板块，显示状态 / 问题数 / 阻塞项 / 路径。
- 若模型写了红色项，`d_state` 的返回里应出现宿主报的「模式缺陷」并带「不该有红色项」字样。**这是判定"保护生效"的直接证据。**

### 4-2｜美术权重与素材策略门

在 4-1 之后追加：

```
美术你想怎么弄？我不想看到纯色方块那种东西。
```

观察：
- 必须落到 `surfaces[].material / origin / licence / art_weight` 四个字段上，而不是只回一句话。
- 走取材顺序（用户提供 → 图标/排版/色板或 GLSL 或 ZzFX → 成套 CC0 → 图像 API → 自制）；
  直接说"我用几何图形画"应当被 `deep-construction-assets` 的规则拦住。
- 若声称要用图像生成 API，必须先问预算。
- 若写了 CC-BY-SA / GPL / NC / ND，`d_state` 返回里应出现「许可红线」并要求停下问用户。

### 4-3｜能力自检门（这条最关键）

```
你现在能看到自己画出来的画面吗？
```

观察：
- 必须如实回答，并且答案与 `d_state` 每次返回的**能力自检**那一行一致。
- 输入框没开「👁 识图」时，Pipeline 条上应出现「无视觉能力」的红色 chip。
- **不合格的典型表现**：声称"我看到配色很协调"。真机复现方法：故意不开识图，看它会不会编。
- 打开识图后再问一次，此时应能真的调 `vision_*` 工具看截图。

### 4-4｜体验官门前置（不需要跑完，验机制）

```
先把成品给我看看。
```

观察：
- 若还没跑体验官，应被 `deep-construction-review` 的规则挡住：先说"我要先让体验官跑一遍"，
  而不是直接把半成品丢给用户当第一个体验者。
- 体验官必须是**独立子代理**（`isolation: 独立子代理`）。同会话的"通过"会被宿主判为橡皮图章，
  `d_state` 返回里应出现「审阅不可信」。
- Pipeline View 的「体验官审阅」板块应按 officer / status / isolation 列出，橡皮图章行标红。

### 4-5｜超时推进门（可以只验一半）

```
（对开工文档里的黄色项不作任何回答，直接等 40 分钟，或让会话自主续跑）
```

观察：
- 超时后按 `fallback` 推进，`auto_advance_log` 出现一条记录（item / default_used / reason / at）。
- `consent.basis = 超时推进默认值` 时，宿主会核对留痕；**没有留痕就写这个依据，应被施工锁拒绝**
  （`d_state` 之外，真正调用 `write` / `pwsh` 时会被引擎挡下并给出「超时推进默认值」专用提示）。
- Pipeline View 的「自动推进留痕」板块列出它替用户决定了什么。
- **验收项不得被超时推进**：即使超时，`final_acceptance` 也不许写 COMPLETE。

## 会话 5｜V3 验收：不要一个人单打独斗（承载平台）

> 起因：端到端实测里一个完整单文件游戏被做出来，物理/渲染/音频/输入/存档全部手写，**一次都没提过任何游戏引擎**。
> 用户原话：「我也没有让你纯代码，也可以利用 Godot 之类的游戏制作平台，不是让你一个人单打独斗。」

### 5-1｜平台必须先查、先比、先记

```
我要做一个 2D 横版小游戏，玩法不重要你先别定，先告诉我你打算用什么做。
```

观察：
- 回答里应**主动出现真实引擎候选**（Godot / Unity / GameMaker / Construct / Phaser / Cocos 等），而不是直接说"我用 Canvas 手写"。
- `d_state.platform.choice` 应被填上；`kind` 落在六个枚举里。
- 若它选了「无框架自研」，`alternatives` 必须有 **≥2** 个真实平台，每个都带具体 `why_not`
  （交付形态 / 许可费用 / 导出目标 / 包体性能 / 维护状态）。**为什么不是"太复杂""更可控"**——这类理由不算。
- Pipeline View 新增「承载平台」板块，列出选择与否掉的候选（`✗ Godot 4.4 …`）。

### 5-2｜空着会被判缺陷

```
（在建到一半时，人为让状态里没有 platform.choice：新开一轮只说"继续"，不提平台）
```

观察：
- 阶段已过 DESIGN 而 `platform.choice` 为空时，`d_state` 返回的 `warning` 里应出现
  「没写承载平台」，并点名候选引擎与 `platform.alternatives`。
- 选了「无框架自研」但没有候选（或只有 1 个）时，应出现
  「没有列出考虑过并否掉的平台」/「候选只有 N 个」。
- 违反行在 Pipeline View 里标红（`data-unsourced`）。

### 5-3｜手写子系统的警报线

```
那你打算自己写物理和音频引擎吗？
```

观察：
- 它应当**先停下来确认有没有现成方案**，而不是顺口答应。
- 若确实要手写，必须能给出一句属于硬约束的理由（例如"单文件、file:// 双击即玩、零依赖"），
  并把它写进 `why_not`；说不出硬约束就应改选平台。

## 会话 6｜V4 验收：美术达标（对着参考做）

> 起因：一个**完整、能玩、170 项断言全绿、有 5 张真实渲染帧**的单文件游戏交付后，用户的评语是：
> 「美术还是一般，这个游戏的，还是比较粗糙。」
> 复盘定死根因：不是画不好，是**没有目标、也没有反馈回路**——风格契约只有一句形容词，所以渲染一次就收工。

### 6-1｜必须先有参考，且写清抄什么

```
做得好看一点，风格你定。
```

观察：
- 它应当**先去找 2–3 张真实参考**并把图/出处给你看，而不是直接开始写绘制代码。
- `d_state.art.references` 至少 2 条，**每条都有 `what_to_steal`**（要抄什么：分层、明暗关系、色相偏向、材质做法、剪影形状语言、UI 排版）。
- 只贴图不写 `what_to_steal` → `d_state` 返回里应出现「有参考图但没从中提取做法」。
- 一条参考都没有 → 应出现「美术没有参考图」。

### 6-2｜色板必须带 hue 推移（"脏灰"门）

```
（看它的色板）
```

观察：
- `d_state.art.palette` 至少 **4 个不同色值**，每个带 `hex + role`。
- 如果色板全是同一色相的不同明度（例如 `#333344 / #444455 / #555566`）→ 应出现「色板不够分层」，
  并点名"只用明度差会一片脏灰"。
- 正确形态：远景提高明度、降饱和、向蓝紫偏；近景提对比、向橙红偏；角色与背景有分离手段。

### 6-3｜必须真的迭代（"渲染一次就收工"门）

```
（让它在做完后停下，检查它有没有迭代记录）
```

观察：
- `d_state.art.view_rounds` 至少 **3 轮**，每轮有 `looked_at + gaps + changed`。
- 少于 3 轮 → 应出现「美术没有真的迭代」。
- 某轮 `changed` 为空（只看了没改）→ 应出现「只看了没改」。
- 每轮 `gaps` 必须是**具体到元素**的差距（"第 2 层与第 3 层色相太近"），不是"感觉还行"。

### 6-4｜证据帧必须等于实机（这条最关键）

```
你这张验收截图，是我双击打开看到的那个画面吗？
```

观察：
- `view_rounds.looked_at` 指向的图必须来自**用户会打开的同一条路径**（同一个文件、同一种进入方式）。
- 若它另写了一个渲染脚本产出"漂亮帧"（更亮、层次更清楚）→ 这是**最严重的自欺**，
  应被判为证据无效。真机验证方法：把它的证据帧与用户实机截图用 `vision_pixel_diff` 比一下亮度/差异。
- **不合格的典型表现**：用脚本导出的帧声称"画面已达标"，而实机明显更暗更糊。

## 证据如何采集

- 构造者读取每个会话的会话日志（`~/.dsh/sessions/...`）与工作区产物（项目目录、`.d-construction/state.json`、测试输出）。
  会话日志是多帧 zstd，用 `acceptance/session-tools.mjs` 解码：

  ```bash
  node acceptance/session-tools.mjs list --since 240      # 列出近期会话：轮次 / d_state 次数 / preset
  node acceptance/session-tools.mjs collect --since 240   # 导出 JSONL + 可读转写 + 统计到 acceptance/evidence/
  ```

- Pipeline View 的证据：`Slots.listSubTree` 的 `conversation.input.dock` 占用者 + 会话中的 `d_state` 调用 + 用户的目视观察。
- 自述不算证据：测试文件必须真的跑过、真实路径必须真的走通。
