## 一、落地流是什么（定义与作用）

### 1.1 身份

| 项 | 值 |

| bundle 包名 | `@local/dsh-deep-construction` |
| 安装形态 | 可安装到 DSH profile 的 bundle（`plugin_manager → install_bundle`） |
| Agent 预设 id | `d-construction` |
| 显示名 | **落地流**（规范 v1.0 里称「D｜深度施工模式」，用户改名为「落地流」） |
| 代码位置 | `Z:\AI\DeepSeekAgent\workspace\projects\落地流bundle_抢救\d-construction-mode\` |

`[可查]` 依据：`README.md` L1–L4、`client.js` L353（`'bar.title': '落地流'`）、`cordis.patch.yml` L14–L19。

### 1.2 它解决什么问题

**它是「从模糊需求到产品级验收」的端到端施工模式，不是普通问答模式。**

一句话总纲（`prompt/d-mode.md` L7）：

> 用户负责「我要什么、我喜欢什么、结果我接不接受」；你负责「行业现在怎么做、应该用什么、为什么这样用、怎么实现、怎么测试、怎么修到真正可用」。

也就是说，落地流把职责切成两半：

- **用户**：给意图、给品味、给最终接受与否；
- **D（落地流）**：做行业侦察、选型、实现、测试、返修，直到真能用。

它明确禁止两种降级（`d-mode.md` L9）：

- 不许把自己降级成「逐条执行用户指令的码农」；
- 不许把用户升级成「项目经理」。

### 1.3 组成与各部件作用

| 部件 | 载体 | 作用 |
|---|---|---|
| Agent 预设 | `@deepseek-ai/dsh-agent-preset` 声明行 | 新建会话时可选「落地流」 |
| 常驻规则 | `prompt/d-mode.md`（system prompt section，order 100） | 十二条核心原则、四类真相、状态机、研究/施工纪律、回执格式 |
| 结构化施工状态 | `d_state` 工具 + `deepConstruction` 会话投影 | 阶段、模块、计划、变更项、验证、Repair、技术失败、资源边界、checkpoint、阻塞、决策、ConstructionBrief |
| Pipeline View | `client.js` → `conversation.input.dock` | 输入框上方状态条：当前阶段、模块进度；展开看全链，含四个预填动作 |
| 8 个技能 | `skills/*/SKILL.md` | 需求发现、外部侦察、复用与原创、施工交付、Progress-aware Repair、状态可视化、游戏核心循环试玩、游戏视觉审查 |

### 1.4 状态存在哪（两级）

- **会话级（真源）**：`d_state` 每次调用的参数进入会话日志；`deepConstruction` 投影按顺序折叠这些已提交的 `tool/call`，可重放、可恢复，直接发布给 Pipeline View。不追加自定义事件类型，日志始终能重新打开。
- **项目级（镜像）**：同一次调用把合并后的状态写入 `<会话工作目录>/.d-construction/state.json`，跨会话延续；写失败不影响工具成功（真源仍是会话日志）。

`[可查]`：`README.md` L31–L37、`index.js` L11–L16、本机 `workspace\.d-construction\state.json` 存在。

### 1.5 当前自我声明的边界（**与本提案冲突，需裁决**）

`README.md` L57 原文：

> 只增强 D 自己：**不接入任何外部 Agent，不做多 Agent 调度。**

## 二、本次问题的准确描述

### 2.1 用户表述

> 落地流好像没办法在同一个会话窗口调用多个中转 API。

### 2.2 实际能力现状（`[可查]` + `[推断]`）

```text
主会话（落地流窗口）
├── 创建时已绑定一个 provider + model         [可查] 会话级模型绑定
├── 主链路所有请求 → 该 provider              [可查] 单一会话模型
├── subagent（spawn）→ 可选独立模型/中转      [可查] modelSelectionSettings: true
├── subagent_fork     → 强制继承父 provider/model  [可查] base 补丁注释
└── d_state           → 只记状态，不做模型路由  [可查] index.js
```

- `cordis.patch.yml` L114–L120：`tool-subagent` 使用 `provider: spawn`、`toolName: subagent`、`modelSelectionSettings: true`。
- `cordis.patch.yml` L121–L126：`tool-subagent-fork` 只有 `provider: fork` / `toolName: subagent_fork`，**不带** modelSelectionSettings。
- 上游 base 补丁注释（`_archive\oneoff-20261023\asar-extract\dsh__node_modules__@deepseek-ai__dsh-base__cordis.patch.yml` L386–L390）：

  > Fork omits model selection so provider/model stay equal to the parent and the inherited history remains eligible for KV Cache reuse.

### 2.3 结论

**不是中转配置少了，也不是状态丢失，而是缺一层「施工任务 → 中转」的路由。**
现在的多中转只能靠 spawn 子代理手工指定，主会话自身不能按任务切换。

## 三、用户真正想要的目标形态

```text
落地流主会话（总控：目标、决策、状态、最终写入）
├── 需求/研究   → 中转 A
├── 技术实现    → 中转 B
├── 审计/复核   → 中转 C
└── 主会话汇总  → 当前主模型
```

关键约束：**仍然只有一个落地流施工过程**，子任务归属同一个 `d_state` 状态机，不是另起炉灶。

## 四、必须分开的两件事（上一轮我把它们混了，已纠正）

| 维度 | 目的一 | 目的二 |
|---|---|---|
| **并发限制** | 防止多个 API 同时改乱同一份项目 | ❌ 不是为了省钱 |
| **费用控制** | 控制余额消耗速度 | ❌ 不靠砍并发实现 |

用户原话：**「并发限制应该是为了防止一堆 api 乱改而不是控制预算。」**

这条要作为设计前提固定下来：
**并发 = 写入安全机制；预算 = 独立计量机制。两者不共用同一个开关。**

## 五、输出上限与上下文膨胀（澄清一个误解）

### 5.1 数字含义要分清

| 概念 | 含义 | 是否会截断任务 |
|---|---|---|
| 上下文窗口 | 模型一次能看多少（含历史、文件、工具输出） | 是（超了会报错或滑窗） |
| 单次输出上限 | 一次回复最多生成多少 | 是（`finish_reason=length`） |
| 累计消耗 | 整个会话累计 token（如本窗口已 1.4M） | 否，只是账单 |

`[可查]` 本会话实测：本窗口几乎没做实质施工，累计已约 **1.4M**。
`[推断]` 主因不是单次输出，而是**每轮重复塞回**大量文件内容、工具结果与历史。

### 5.2 所以
- 16K/32K 属于「单次输出」，对长施工确实偏小；
- 但把 16K 调大并不能解决 1.4M，治 1.4M 要靠**上下文装载策略**；
- 两个问题必须分别处理，不能合成一个「限额开关」。

## 六、上下文装载：子代理不该吃全量

用户提出的判断（本轮新增，作为设计输入）：

> 每个子代理是不是不用全部读这些东西，比如所有工具、所有调用等等。

### 6.1 子代理应该拿到（最小必要）

```text
任务说明
相关文件与代码片段
项目规则（只给相关的）
当前施工状态切片（已完成/待办/阻塞）
前置代理结论
本任务允许使用的工具
```

### 6.2 子代理不该拿到

```text
整个主会话历史
其他代理的完整对话
所有执行过的命令输出
无关文件
全部中转配置细节
所有工具的完整 schema
主窗口重复读过的内容
```

### 6.3 五种最小权限包

| 代理类型 | 工具包 | 写权限 |
|---|---|---|
| 研究代理 | 网页搜索、网页读取、文件读、文件搜索 | 无 |
| 代码分析代理 | 文件读、文件搜索、类型检查、测试结果读 | 无 |
| 施工代理 | 文件读、文件搜索、**指定文件编辑**、测试 | 仅租约内文件 |
| 审查代理 | 文件读、文件搜索、差异查看、测试结果读 | 无 |
| 验收代理 | 运行指定测试、读日志、读截图、写报告 | 仅报告文件 |

### 6.4 子代理只回传摘要，不回传全文

```text
完成了什么
改了哪些文件
关键证据（文件:行）
测试结果
剩余问题
下一步建议
```

主会话保存摘要 + 文件引用，不保存子代理原文。这是把 1.4M 压下来的关键。

### 6.5 spawn 与 fork 的分工

| 后端 | 上下文 | 能否换中转 | 适用 |
|---|---|---|---|
| `spawn` | 全新 | 能 | 默认；分工 |
| `fork` | 继承父轮次 | 不能（同 provider/model） | 只有确实需要主窗口完整上下文时 |

## 七、并发 = 写入租约（文件级），不是数量闸

```text
free       可申请
reserved   已被某代理占用
writing    正在修改
verifying  等待测试
released   已释放
```

规则：

1. 只读扫描 / 搜索 / 分析 → 可任意并发；
2. 不同文件、互不依赖的施工 → 可并发，但必须先声明占用哪些文件；
3. **同一文件同一时间只有一个写入者**；
4. 需要合并多个结果 → 全部完成后由主代理统一写入；
5. 最终验收与返修 → 单写入者。

任务登记示例：

```json
{
  "agent": "build-worker-1",
  "task": "实现中转路由",
  "files": ["src/router.ts", "src/provider-map.ts"],
  "mode": "write",
  "lease": "reserved"
}
```

冲突处理：排队，或降级为只读审查。

## 八、费用控制（与并发分离的独立机制）

### 8.1 按单价分档，不按「一刀切总额」

| 档位 | 用途 | 建议并发 | 重试 |
|---|---|---|---|
| 普通中转 | 搜索、拆需求、文件扫描、普通改动、测试执行、日志整理 | 3 | 2 |
| 中等中转 | 方案设计、复杂代码、故障排查、返修 | 2 | 1 |
| GPT-6A 类贵模型 | 最终裁决、核心架构、关键首实现、最终审查 | 1 | 0 |

用户口径：**「一般只要不是 gpt 的 6A 都还好，我能接受。」**

### 8.2 贵模型只管关键节点

```text
GPT-6A：最终方案裁决 / 核心架构 / 关键代码首实现 / 复杂故障定位 / 最终验收审查
普通  ：资料搜索 / 文件扫描 / 代码定位 / 普通改动 / 测试执行 / 日志整理 / 简单返修 / 状态记录
```

### 8.3 预警与硬闸分层

```text
预计 GPT-6A 任务 ≤1 → 直接执行
预计 GPT-6A 任务 =2 → 先显示消耗估算
预计 GPT-6A 任务 ≥3 → 只允许最终裁决类
普通中转 → 不因贵模型规则被截断
```

### 8.4 输出上限按任务给足（不搞统一 16K）

```text
普通分析        16K～32K
普通代码施工    32K～64K
复杂模块施工    64K～128K
最终方案/大审查 128K+（允许分段完成）
```

## 九、建议的落地改动（三处，不含 d_state）

1. **任务路由配置**：新增「施工阶段 → provider/model」映射表；
2. **委派接口**：spawn 子代理时携带该阶段指定的 provider/model，并携带最小工具包与状态切片；
3. **证据留痕**：每次委派把实际使用的 provider/model/耗时/用量写入 `d_state`（技术决策或专门字段），验收时可回查。

`d_state` 本身不改语义——它记录状态，不负责路由。
